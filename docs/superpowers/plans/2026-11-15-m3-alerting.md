# M3 – Alerting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The server evaluates the triggers from the configuration repository as values arrive, opens and closes problems, detects hosts and items that stopped reporting, and sends an e-mail when a problem starts and when it ends.

**Architecture:** Evaluation is a pure function from (triggers, stored trigger state, new values) to a list of state updates and problem transitions; the store applies that result for one host inside one PostgreSQL transaction that also writes the e-mails to send into an outbox table. A second loop decides "no data" from arrival times, and a third delivers the outbox through a channel interface whose first implementation is SMTP. Nothing is kept in process memory between requests.

**Tech Stack:** Rust 2024, sqlx/PostgreSQL, axum, tokio, lettre (SMTP over rustls), Mailpit in the end-to-end check.

**Spec:** `docs/superpowers/specs/2026-11-14-cerbrix-design.md` (sections 5.2, 5.6, 5.7 "Removed hosts", 5.8). Issues #25–#29, and the point carried over from #22.

## Global Constraints

- License Apache-2.0; English for code, comments, documentation and commit messages.
- `unsafe_code = "forbid"`. `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace` and `cargo test --workspace` pass after every task.
- No server state only in process memory: trigger state, problems and pending notifications live in PostgreSQL. A second server instance must reach the same decisions.
- Value ingest keeps no state in the process; everything it needs comes from the database inside the request.
- Jobs that must run once (the no-data check, sending notifications) are safe when two instances run them at the same time.
- Every value keeps its measurement time. Values older than the tolerance are stored but never open or close a problem and never send an e-mail.
- "No data for X" is based on arrival at the server, not on measurement time.
- Severities are exactly `info`, `warning`, `high`, `critical`.
- Secrets (the SMTP password, credentials) never appear in logs, error messages, `Debug` output or the database in plain text.
- Dependencies are added with `cargo add` at the latest stable version; shared versions go in `[workspace.dependencies]`.
- Database tests use `#[sqlx::test(migrations = "./migrations")]` and need `DATABASE_URL=postgres://cerbrix:cerbrix@localhost:5432/cerbrix`.

## Decisions this plan makes

The spec leaves these open. Each is the author's call and is listed so the project owner can overrule it.

| # | Decision | Why |
|---|---|---|
| A1 | Triggers are evaluated inside the request that delivers the values, after the values are stored | "As values arrive"; no queue to operate. If evaluation fails the agent gets 503 and resends; evaluation is idempotent |
| A2 | A problem's start time is the measurement time of the value that fired the trigger, after any hold duration has passed | The moment the condition became an alarm; the hold itself is visible in the trigger |
| A3 | Values older than 5 minutes (`alerting.max_value_age_secs`) are not evaluated | Spec: "a few minutes old (configurable)" |
| A4 | A host whose agent clock is so wrong that all its values fall outside the tolerance gets a warning in the server log, at most once per hour per host | Otherwise such a host would silently never alarm |
| A5 | A host with an item-level no-data trigger must also have a host-level `no data for …` trigger; the sync rejects the revision otherwise | #26: an agent outage must give one problem. While a host is silent as a whole, only its host-level trigger fires; without one an outage would give no problem at all |
| A6 | No-data only counts from the first value a host ever sent | A host that is in Git but not yet installed should not alarm |
| A7 | After the server itself was down or not checking, silence is measured from the moment it resumed | Otherwise every host would look silent for the length of the server's own outage |
| A8 | A notification rule matches a host that is in all of the rule's `groups`; no groups means every host | Same meaning as a dashboard's host selection |
| A9 | The end of a problem is mailed to everyone who was mailed its start, whatever the rules say by then | Nobody is left with an alarm that never ends |
| A10 | Problems of a removed host, and problems of a trigger that no longer exists, are closed by the sync with a reason, and the end is mailed | Carried over from #22; an alarm for something that is no longer monitored must not stay open |
| A11 | Acknowledging does not stop the end-of-problem e-mail | Acknowledgement says "someone has it", not "do not tell me" |
| A12 | Without SMTP settings no e-mail is queued; problems are still recorded | #29: "only appears on the dashboard" |
| A13 | An e-mail that cannot be delivered is retried with growing pauses (1 min doubling to 1 h) for 24 hours, then given up and logged as an error | #28: retried and visible in the logs |
| A14 | Problems are listed and acknowledged with `cerbrix-server admin problem …` in this milestone; the HTTP API and the UI come with M4 | There is no user login before M4 |
| A15 | E-mails are plain text in English with times in UTC | Smallest thing that works everywhere |

## Review Focus

1. The same batch arrives twice (the agent resends after a 503), or values arrive out of order: no problem is opened twice, none flaps, no e-mail is sent twice. → Tasks 1, 3, 4.
2. The server restarts in the middle of a hold duration: the hold continues from the stored state and fires on time. → Tasks 1, 3.
3. The server was down for ten minutes: no host is reported silent because of the server's own gap. → Task 5.
4. The mail server is unreachable for an hour and a problem starts and ends in that time: both e-mails arrive afterwards, the start before the end; after 24 hours a message is given up and logged. → Tasks 7, 8.
5. A host or a trigger is removed from the repository while its problem is open: the problem is closed with a reason and the recipients are told. → Task 6.

```rust
// alerting/mod.rs
pub type Params = BTreeMap<String, String>;
/// Canonical text of an instance: "" for no parameters, otherwise `k=v` pairs
/// sorted by key and joined with ",", e.g. `mount=/`.
pub fn instance_key(params: &Params) -> String;
pub struct ActiveTrigger { pub name: String, pub severity: Severity, pub expression: String, pub expr: TriggerExpr }
/// Parses the host's triggers; one that does not parse is skipped and logged at error level.
pub fn active_triggers(host: &EffectiveHost) -> Vec<ActiveTrigger>;
#[derive(Debug, Clone, PartialEq)]
pub struct TriggerState { pub trigger: String, pub instance: String, pub firing: bool,
    pub condition_since_ms: Option<i64>, pub last_ts_ms: i64, pub last_value: Option<f64> }
#[derive(Debug, Clone, PartialEq)]
pub struct OpenProblem { pub trigger: String, pub instance: String, pub severity: Severity,
    pub at_ms: i64, pub summary: String }
#[derive(Debug, Clone, PartialEq)]
pub struct ResolveProblem { pub trigger: String, pub instance: String, pub at_ms: i64 }
#[derive(Debug, Default, PartialEq)]
pub struct Evaluation { pub states: Vec<TriggerState>, pub open: Vec<OpenProblem>,
    pub resolve: Vec<ResolveProblem>, pub too_old: usize }

// alerting/eval.rs
pub fn evaluate(triggers: &[ActiveTrigger], states: &[TriggerState], values: &[MetricValue],
    now_ms: i64, max_age_ms: i64) -> Evaluation;
```

Rules of `evaluate` (only `TriggerExpr::Compare` triggers; `NoData` triggers are ignored here):
- A value matches a trigger when the keys are equal and every parameter of the selector is present in the value with the same value. The instance is the value's full parameter set.
- A value with `ts_ms < now_ms - max_age_ms` is counted in `too_old` and otherwise ignored.
- For each (trigger, instance), the matching values are processed in ascending `ts_ms`. A value whose `ts_ms` is not greater than the stored `last_ts_ms` is ignored.
- Condition true: `condition_since_ms` is set to this value's time if it was `None`. The trigger fires when there is no hold, or `ts_ms - condition_since_ms >= hold`. On the transition to firing, one `OpenProblem` with `at_ms = ts_ms`.
- Condition false: `condition_since_ms = None`; if it was firing, one `ResolveProblem` with `at_ms = ts_ms`, and `firing = false`.
- `states` in the result holds the new state of every (trigger, instance) that received at least one value that was not ignored. Order: by trigger, then instance.
- `summary` is `"<expression>: value <v>"`, the value printed with at most 3 decimals and no trailing zeros, with ` on <instance>` appended when the instance is not empty. Example: `disk.used_percent > 90 for 10m: value 96.5 on mount=/`.
- Comparison uses `f64` operators directly (`==` and `!=` are exact).

  - `fires_without_hold`: `cpu.usage > 90`, value 95 → one open at that time, state `firing`, summary `cpu.usage > 90: value 95`.
  - `does_not_fire_below_threshold`: value 90 → no open, state not firing, `condition_since_ms == None`.
  - `every_operator`: `>`, `<`, `>=`, `<=`, `==`, `!=` against 90 with values 89, 90, 91.
  - `hold_needs_the_full_duration`: `> 90 for 10m`, values 95 at t, t+5m, t+10m (given in one call with a large max age) → open only at t+10m; given the first two only → no open, `condition_since_ms == Some(t)`.
  - `hold_continues_from_stored_state`: stored state `condition_since_ms = t`, one new value at t+10m → open.
  - `dip_resets_the_hold`: 95, 80, 95 within the hold → no open; `condition_since_ms` is the third value's time.

  - `nodata_triggers_are_ignored`, `unparsable_trigger_is_skipped` (via `active_triggers` on an `EffectiveHost` with one bad expression → one trigger).
  - `summary_formats_value_and_instance`: 96.5 on `mount=/`; 95.0 prints `95`; 0.123456 prints `0.123`.

```rust
pub enum EventKind { Started, Resolved }          // as_str(): "started" | "resolved"
```

- `resolve_reason` values are `condition_ended`, `host_removed`, `trigger_removed`; the body prints them as `the condition no longer holds`, `the host was removed from the configuration`, `the trigger was removed from the configuration`.

```rust
impl StateStore {

    /// state upserts, problems opened and resolved, outbox rows. One transaction.

        -> Result<Vec<ProblemEvent>, StateError>
```

Migration `0003_m3.sql`:

```sql
ALTER TABLE hosts ADD COLUMN last_seen_at timestamptz;

CREATE TABLE trigger_states (
    host_id         uuid NOT NULL REFERENCES hosts (id) ON DELETE CASCADE,
    trigger_name    text NOT NULL,

);

CREATE TABLE problems (

    trigger_name    text NOT NULL,
    instance        text NOT NULL,

    summary         text NOT NULL,
    started_at      timestamptz NOT NULL,
    resolved_at     timestamptz,
    resolve_reason  text CHECK (resolve_reason IN ('condition_ended', 'host_removed', 'trigger_removed')),
    acknowledged_at timestamptz,
    acknowledged_by text,
    ack_comment     text
);
CREATE UNIQUE INDEX problems_one_open ON problems (host_id, trigger_name, instance) WHERE resolved_at IS NULL;
CREATE INDEX problems_started ON problems (started_at DESC);

CREATE TABLE series_seen (
    host_id      uuid NOT NULL REFERENCES hosts (id) ON DELETE CASCADE,
    item_key     text NOT NULL,
    instance     text NOT NULL,
    last_arrival timestamptz NOT NULL,
    PRIMARY KEY (host_id, item_key, instance)
);

CREATE TABLE alerting_state (
    singleton    boolean PRIMARY KEY DEFAULT true CHECK (singleton),
    heartbeat_at timestamptz,
    baseline_at  timestamptz
);
INSERT INTO alerting_state DEFAULT VALUES;

CREATE TABLE notification_outbox (
    id              bigserial PRIMARY KEY,
    problem_id      uuid NOT NULL REFERENCES problems (id) ON DELETE CASCADE,
    event           text NOT NULL CHECK (event IN ('started', 'resolved')),
    recipient       text NOT NULL,
    created_at      timestamptz NOT NULL,
    attempts        integer NOT NULL DEFAULT 0,
    next_attempt_at timestamptz NOT NULL,
    locked_until    timestamptz,
    sent_at         timestamptz,
    failed_at       timestamptz,
    last_error      text,
    UNIQUE (problem_id, event, recipient)
);
CREATE INDEX outbox_due ON notification_outbox (next_attempt_at) WHERE sent_at IS NULL AND failed_at IS NULL;
```

`evaluate_host`:
- `SELECT … FROM hosts WHERE id = $1 AND active FOR UPDATE`; an inactive or unknown host returns no events and does not call `decide`.
- Opening: `INSERT … ON CONFLICT DO NOTHING` on the one-open index; an event only when a row was inserted. `started_at` from `at_ms`.
- Resolving: update the open problem of (trigger, instance) with `resolved_at` and reason `condition_ended`; an event only when a row changed.
- With `queue_mail`: for a started event, `recipients(rules, severity, groups)` with the rules read from `config_documents` (kind `notification`) in the same transaction; one outbox row per address with `next_attempt_at = created_at = ` the problem's time. For a resolved event, one row per recipient of that problem's `started` rows.
- `claim_notifications`: rows with `sent_at IS NULL AND failed_at IS NULL AND next_attempt_at <= now AND (locked_until IS NULL OR locked_until < now)`, oldest id first, `FOR UPDATE SKIP LOCKED`, at most `limit`; sets `locked_until = now + 5 min` and `attempts = attempts + 1`; returns each with its `Notification` built from the problem. A `resolved` row is not returned while the same problem's `started` row for that recipient is still unsent and not failed.
- `mark_notification_retry` clears `locked_until`, stores the error cut to 500 characters. `last_error` never contains the SMTP password (the caller passes channel errors, see Task 7).
- `acknowledge_problem`: sets the three fields; acknowledging again overwrites them; `by` and `comment` are cut to 200 and 1,000 characters.
- `problems`: `Open` = unresolved, most severe first then oldest; `All` = newest first.

**Files:**

```rust
// config.rs — Config gains `#[serde(default)] pub alerting: AlertingConfig` and `pub smtp: SmtpConfig` (Task 7 adds smtp)
pub struct AlertingConfig { pub max_value_age_secs: u64 /* default 300, 10..=86400 */,
                            pub nodata_check_secs: u64 /* default 15, 5..=300 */ }
// state/alerting.rs
impl StateStore {
    /// Sets hosts.last_seen_at and upserts series_seen for the given (key, instance) pairs.
    pub async fn touch_seen(&self, host_id: Uuid, now: OffsetDateTime, series: &[(String, String)])
        -> Result<(), StateError>;

```

In `POST /api/agent/v1/values`, after the metrics store accepted the values:
1. `touch_seen(host.id, now, series)` where `series` are the (key, instance) pairs of accepted values that match the selector of one of the host's `NoData` triggers with a selector. (Host-level no-data needs only `last_seen_at`.)
2. `evaluate_host(host.id, queue_mail, |ctx| evaluate(&active_triggers(cfg), &ctx.states, &accepted, now_ms, max_age_ms))`; a host without stored configuration has no triggers. `queue_mail` is whether SMTP is configured (until Task 7: `false`).
3. A store error in step 1 or 2 is logged and answered with `503` and code `alerting_unavailable`, so the agent keeps the batch and resends it. The response for success is unchanged.
4. When `too_old > 0` and no value of the batch was evaluated, log one warning naming the host, at most once per hour per host. The "once per hour" memory is a small in-process map; it only limits log lines and is not server state.

The agent treats this 503 as retryable already (any 5xx). Values are written to the metrics store before evaluation, so a resend writes the same samples again; the metrics store keeps one sample per timestamp.

```rust
// alerting/nodata.rs
pub struct Seen { pub last_seen_ms: Option<i64>,
                  pub series: Vec<(String /*key*/, Params, i64 /*last arrival ms*/)> }
pub fn evaluate_nodata(triggers: &[ActiveTrigger], states: &[TriggerState], seen: &Seen,
    baseline_ms: Option<i64>, now_ms: i64) -> Evaluation;
pub async fn check_once(store: &StateStore, queue_mail: bool, check_every: Duration,
    now: OffsetDateTime) -> Result<usize /*hosts checked*/, StateError>;
pub async fn run_nodata_loop(store: StateStore, queue_mail: bool, check_every: Duration,
    shutdown: CancellationToken);
// state/alerting.rs
impl StateStore {
    /// Updates the heartbeat. If the previous heartbeat is missing or older than
    /// 3 × check_every, sets baseline_at = now. Returns the baseline.
    pub async fn alerting_heartbeat(&self, now: OffsetDateTime, check_every: Duration)
        -> Result<Option<OffsetDateTime>, StateError>;
    pub async fn hosts_with_nodata_triggers(&self) -> Result<Vec<Uuid>, StateError>;
    pub async fn seen(&self, host_id: Uuid) -> Result<Seen, StateError>;
}
```

Rules of `evaluate_nodata` (only `NoData` triggers):
- "Silent since" for the host is `max(last_seen_ms, baseline_ms)`; for a series `max(last arrival, baseline_ms)`.
- A host that never sent a value (`last_seen_ms == None`) produces nothing.
- Host-level trigger (no selector), instance `""`: fires when `now - silent_since >= window`; resolves when it is firing and that no longer holds.
- Item-level trigger: one instance per series in `seen` that matches the selector. It fires when that series is silent for the window **and** the host as a whole is not (`now - host_silent_since < window`). When the host as a whole is silent for the window, item-level triggers do not fire, and one that is firing stays as it is.
- An item-level trigger resolves when its series reported again.
- `OpenProblem.at_ms` and `ResolveProblem.at_ms` are `now_ms`. Summary: `no data for 3m` or `cpu.usage: no data for 5m`, with ` on <instance>` for an instance.
- State rows use `last_ts_ms = now_ms`, `last_value = None`.

`check_once`: `alerting_heartbeat`, then for every host of `hosts_with_nodata_triggers` one `evaluate_host` with `evaluate_nodata`. Two instances running it at once are safe because `evaluate_host` locks the host and the open-problem index is unique. `run_nodata_loop` calls it every `check_every`, logs store errors and continues, and survives a panic in a cycle the way the sync loop does. `serve` starts it and awaits it on shutdown.

`compile` gains rule A5: a host whose effective triggers include an item-level no-data trigger but no host-level one is an issue at the host file: `trigger "<name>" watches one item for missing data; add a host-level trigger such as "no data for 5m" so that an agent outage is one problem`.

```rust
pub enum ChannelError { Retryable(String), Permanent(String) }
#[async_trait] pub trait Channel: Send + Sync {

    async fn send(&self, to: &str, notification: &Notification) -> Result<(), ChannelError>;
```

**Files:**

- Modify: `crates/cerbrix-server/src/tls.rs`, `crates/cerbrix-server/src/api/mod.rs` (`AppState` gains `queue_mail: bool`), `crates/cerbrix-server/src/api/agent.rs`, `crates/cerbrix-server/src/gitops/sync.rs`

**Interfaces:**
- Consumes: `Channel`, the outbox methods of Task 3, `SmtpConfig::enabled`.
- Produces:

```rust
pub const GIVE_UP_AFTER: Duration = Duration::from_secs(24 * 3600);
pub fn retry_delay(attempts: i32) -> Duration;      // 1 min, 2, 4, … capped at 1 h
pub async fn dispatch_once(store: &StateStore, channel: &dyn Channel, now: OffsetDateTime)
    -> Result<usize /*sent*/, StateError>;
pub async fn run_dispatch_loop(store: StateStore, channel: Arc<dyn Channel>,
    every: Duration /* 5 s in serve */, shutdown: CancellationToken);
```

- `dispatch_once` claims up to 20 notifications and sends them one after another. Success → `mark_notification_sent`, one `info` line (problem, event, recipient). `Retryable` → if `now - created_at >= GIVE_UP_AFTER` then `mark_notification_failed` and one `error` line saying the message was given up; otherwise `mark_notification_retry` with `now + retry_delay(attempts)` and one `warn` line. `Permanent` → `mark_notification_failed` and one `error` line.
- A send that takes longer than the lease cannot run forever: the channel's own timeout (Task 7) is far below the 5-minute lease.
- `serve`: with `smtp.enabled()`, build the channel (a build error stops the start), start the loop, and pass `queue_mail = true` to the ingest handler, the no-data loop and the Git sync. Without SMTP, no loop, `queue_mail = false`, and one `info` line at start: `no SMTP server configured; problems are recorded but no e-mail is sent`.
- All three loops (sync, no-data, dispatch) are awaited on shutdown.
